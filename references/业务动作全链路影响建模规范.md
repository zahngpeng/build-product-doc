# 业务动作全链路影响建模规范

## 一、适用范围与内容归属

当任务涉及动作结果分析、业务逻辑完整性／闭环审核、影响上下游结果的变更，或需要用图表表达跨模块影响时，使用本规范。只分析本次涉及的动作和依赖，不因读取规范扩大交付范围。

本规范固定分析方法，不固定行业对象、表格列、参与者、状态或事件时点。具体内容从当前项目事实动态识别。分析结果写入对应模块的《业务流程与状态流转》；无法归入单一模块的跨模块流程写入产品总PRD。只有用户明确要求时才单独成文档。需要模板时使用[业务动作全链路影响分析模板](../assets/模板/业务模块主文档/业务动作全链路影响分析模板.md)，作为章节片段插入。

先完整建模，再按读者需要组织交付。分析清单用于覆盖检查和追踪，不代表正文必须先展示全部编号，也不要求每个动作配齐所有图表。通用的读者、编号、术语和示例约定见[产品文档内容规范](产品文档内容规范.md)的“阅读与表达”。事实不足按 SKILL.md 的决策规则处理，保留待确认问题，不套用其他项目的规则。

## 二、核心概念

| 概念 | 定义 |
|---|---|
| 业务动作 | 用户、系统、定时器或外部事件可以独立触发，并可能产生可观察业务结果的操作 |
| 场景 | 同一业务动作在一组明确前置状态和条件下的一次结果组合 |
| 影响面 | 被动作独立生成、更新、锁定、释放、冲回、失效、重算或通知的业务对象或稳定事实 |
| 事件时点 | 影响真正落地的项目实际业务事件，不等同于页面按钮点击时间 |
| 原子组 | 必须全部成功或全部失败的一组同步结果 |
| 补偿 | 结果已经提交后，通过新的反向业务动作恢复一致性 |

## 三、建模步骤

### 1. 建立业务动作目录

读取本次范围必需的项目级文档、模块主PRD、功能清单、流程、字段字典、页面PRD、集成约定和验收内容，识别：

- 页面动作，例如保存、提交、撤回、重提、审核、关闭和作废；
- 系统动作，例如自动生效、任务生成、状态重算和超时处理；
- 外部事件，例如支付回调、物流回传、设备上报和第三方审批结果；
- 下游履约与逆向动作，例如实际执行、取消、凭证失效、冲回和补偿。

页面动作对应实际入口和按钮；系统动作、外部事件对应真实触发事件。进入页面、确认一条记录、提交主单、最终审核通过和实际执行产生不同结果时，分别建立动作或场景，不能用“新增”“完成”等宽泛名称掩盖差异。

| 动作ID | 动作名称 | 触发主体 | 入口或事件 | 前置状态 | 作用范围 | 来源 |
|---|---|---|---|---|---|---|

完成条件：本次范围内每个可能产生独立副作用的触发事件都有动作ID；纯导航动作只有在需要明确“不产生业务数据”时才纳入。

### 2. 动态发现影响面

从项目事实中提取可能被动作改变的业务对象和稳定事实，建立清单。

| 影响面ID | 项目业务名称 | 对象类型 | 归属模块或系统 | 适用动作ID | 独立性依据 | 允许的变化方式 | 来源 |
|---|---|---|---|---|---|---|---|

对象类型按项目产生，如业务单据、审批实例、任务、凭证、流水、余额、额度、占用、汇总、状态、通知、操作记录或外部请求，只帮助归类，不限制表头。

满足以下任一条件时，作为独立影响面逐项说明；采用横向影响矩阵时独立成列：

- 可以独立生成、更新或失效；
- 拥有独立编号、状态或查看入口；
- 归属不同模块、服务或外部系统；
- 发生时点不同；
- 可以独立失败、重试、作废、回滚或补偿；
- 会被其他业务对象独立引用；
- 对金额、数量、库存、额度、余额或进度产生独立影响。

只有生命周期、归属、发生时点、失败边界和回退方式均一致，且项目将其定义为同一稳定事实时，才允许合并。使用项目真实名称，不以“相关数据”“相关单据”“生成下游数据”或“状态相应变化”代替逐项结果。

完成条件：每个候选影响面都已独立列出，或记录不独立列出的事实依据。表格转置、拆分不改变影响面的独立性。

### 3. 动态建立事件时点

从项目实际事件链建立时点清单，不要求项目具备固定的保存、审核、履约、结算或作废阶段。

| 时点ID | 项目时点名称 | 适用动作ID | 触发事件 | 前置条件 | 责任主体 | 同步或异步 | 来源 |
|---|---|---|---|---|---|---|---|

识别用户触发、校验完成、数据受理、业务决策、生效、下游执行、外部回调、结算和逆向处理等候选阶段，只保留当前项目真实存在的事件。一个动作可以跨多个时点，同一影响面也可以因场景不同而在不同时点变化。

每个实际变化都能读出“变化方式＋发生时点”，例如“保存成功时生成”“取消成功时释放”。同表结果时点一致时可在表前统一说明，例外逐项标出；不必每个单元格重复编号。“不生成”“不变化”“不适用”按需说明判断时机。未确认的时点写明 `[待确认]`，不能默认发生在提交或审核阶段。

完成条件：正文、表格和图形中的每个时点都有定义及项目依据；点击、业务成功和后台后续处理没有混为同一事件。

### 4. 穷举场景并串联闭环

根据项目实际规则选择会改变结果的拆分维度：

- 前置状态、数量、金额、批次、范围或处理方式；
- 审批、权限、策略、主数据、资源和外部依赖可用性；
- 同步成功、明确失败、处理中、超时和异步回调；
- 并发冲突、重复提交和幂等查询；
- 下游未开始、部分完成、全部完成或已失效；
- 撤回、取消、关闭、作废、回滚和补偿。

只采用有项目依据或影响结果的维度，不机械创建不存在的能力。每个场景表达一组确定条件和结果，结果不同的条件分别保留场景ID。相同处理可集中说明，但场景到处理规则的对应关系必须可定位。

按实际操作链核对“上游触发 → 本次变化 → 下游消费 → 结束或逆向处理”。项目同时存在计划与实际结果、登记与资金执行等不同事实时，分别核对数量、金额和状态，不能仅因一张任务结束就推定其他对象均已完成。

完成条件：适用的主流程、条件分支、依赖失败、并发重试和逆向处理均有结果；跨模块口径一致，无法证明的闭环保留待确认。

## 四、面向读者的展示

### 1. 默认正文：按页面与操作说明

多动作分析按页面或业务旅程分组，自动事件单独说明或紧跟其来源动作。单动作请求直接进入该动作，不扩展整个模块。每个动作让读者依次理解：

1. 在哪个页面、谁能操作、做什么；自动事件则说明由什么触发；
2. 什么条件下、到哪个时点才真正产生影响；
3. 每个独立对象怎样改变，必要时给出前后值或计算口径；
4. 哪些容易误解的对象不会生成、不变化或不重复生成；
5. 完成后的各对象状态，以及在哪里查看结果；
6. 哪些情况会被拦住，失败后保留什么，在哪里恢复或纠错。

以下是可调整的呈现形状，不是每个动作的必填表格数量：

| 会影响什么 | 具体变化 | 什么时候发生 |
|---|---|---|

多个场景要让差异能直接比较。可先说明共同结果，再用中文场景标题和小表列差异；也可使用横向矩阵。不同对象分别成行或列，不能为了短表把独立结果合并。需要说明的“不变化”等结果同样保留，范围外且没有澄清价值的对象不必逐项填“不适用”。

### 2. 图形选择：按表达目的判断

| 需要讲清什么 | 适合的表达 |
|---|---|
| 页面操作、业务步骤、条件分支、结果去向 | 流程图 |
| 不同角色或模块之间的先后交互、同步或异步、共同成功边界、结果产生时点 | 时序图 |
| 单步操作、少量独立结果，文字或小表已足够清楚 | 不配图 |

自行判断哪种图更容易表达，用户指定图形时尊重其选择。已有流程图或时序图能清楚表达且符合事实时可保留；不为统一形式改图，也不要求每个动作配图。同一内容通常选一种；两种图只有分别回答不同问题时才同时保留。

图形节点、参与者和消息采用项目实际名称。图用来解释关系，表格承载逐项影响与必要场景；避免把穷举细节全部塞入图中。流程图的路径、时序图的先后及分支，都与正文中的条件、时点和结果一致。

### 3. 异常、状态与后续处理

按具体动作区分校验阻断、明确失败、结果未知、重复提交和后续处理失败，适用时说明：

| 遇到什么情况 | 哪些结果生效或保留 | 去哪里、怎么处理 |
|---|---|---|

同一次操作必须一起成功的结果、可独立保留的前序结果以及异步后续处理分别说明。提交前或同一事务内失败用回滚表达；结果已提交后通过新业务动作恢复用补偿表达。读取失败和结果未知不能直接写成业务失败，也不能据此重复执行或新增稳定业务状态。

相同的通用处理集中在公共章节，各动作保留可定位引用及特有的失败条件、反馈、恢复入口、权限、重试限制和通知／操作记录要求。去重后仍能知道每个场景适用哪条规则；不能统一写成“失败后重试”。

不同状态对象分别说明动作前后状态与可回退条件。加载中、请求失败和超时默认属于操作反馈；只有项目明确将其定义为稳定业务事实时才进入状态机。

### 4. 技术追踪与横向矩阵

动作、影响面、时点和场景清单可以作为追踪附录，使用中文名称与正文链接建立对应关系。既有ID保留，首次出现时解释其用途；追踪编号不是用户要输入的业务单号。已有权威定义继续引用，不因移动位置重新定义；元数据与定义表遵守[脚本与校验约定](脚本与校验约定.md)。

用户要求技术审计、完整横向矩阵或逐列比较时，保留相应明细。下列是需覆盖的信息，可按问题拆成子表，不要求拼成一张超宽表：

- 上下文：场景ID／名称、动作ID／名称、触发主体、入口或事件、前置状态、触发条件；
- 动态结果：每个相关影响面独立成列，使用项目名称；ID在表头旁或映射表中可查。只纳入至少一个场景会改变或需要明确判断的影响面；
- 控制信息：最终状态、共同成功边界、失败后保留、回滚或补偿、恢复／重试／幂等、通知／操作记录、规则／验收来源；
- 异常详情：异常ID、动作／场景、失败时点及影响面、已提交结果、独立保留、同步回滚、异步补偿、用户反馈、恢复入口、重试限制与来源；
- 状态详情：场景、状态对象、动作前状态、事件时点、动作后状态、是否可回退、回退条件及来源。

按对象或模块拆表时复用同一组场景标识，便于横向比对。每个实际变化均能定位到其时点和依据。既有编号可放附录，但业务人员需要理解的条件、异常和结果不能只留在附录里。

## 五、结果语义

采用下列准确含义；按事实判断变化，不能仅靠替换术语或文字前缀推断对象是否改变。

| 语义 | 使用方式 |
|---|---|
| 生成 | 本场景新建独立对象，并标明时点 |
| 更新 | 写明原值、目标值或计算方式，并标明时点 |
| 锁定／释放 | 写明对象、数量或范围，并标明时点 |
| 增加／减少／冲回／重算 | 写明口径和时点；重算不等于必然增加或减少 |
| 失效／作废 | 写明对象、业务含义和时点 |
| 条件生成 | 同时写明条件和时点 |
| 不生成 | 本动作明确不会创建该对象 |
| 不变化 | 对象已存在，但本动作不改变它 |
| 不重复生成 | 对象已由前序动作生成，本动作只引用或更新 |
| 不适用 | 该影响面不属于本场景，并写明原因 |
| 整体回滚 | 本原子组的结果全部撤销 |
| 独立保留 | 已提交且不属于当前原子组，当前动作失败不撤销 |

## 六、完成检查

分别检查，不以图表、编号或场景数量作为完成标准：

- **结构与追踪**：范围、引用、稳定ID、定义与正文映射完整；重排没有丢失场景或产生重复定义。报告实际校验结果及未检查部分。
- **业务闭环**：动作覆盖实际触发事件；独立影响面逐项保留；实际变化均有时点；适用的分支、异常、并发重试及逆向处理有明确结果。核对上游、本次与下游数量、金额、状态及失败边界，未确认事项明确列出。
- **可读性**：代表性主流程、分支与失败场景不靠查编号也能回答“去哪操作／由什么触发、何时生效、什么改变或不变、在哪里看结果、失败后怎么办”；图形选择有助于理解，图表与正文一致，技术追踪没有遮住业务说明。
