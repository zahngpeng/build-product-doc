# 脚本与校验约定

脚本适用于本 Skill 的文档类型和元数据约定。先看当前脚本的 --help 获取参数；已有项目采用不同约定时使用相应校验工具或人工审核，不为适配脚本迁移整套文档。

## 环境

使用当前环境可用的 Python 3.10 或更高版本。示例中的 python 代表实际解释器；Windows 若命中 WindowsApps 占位程序，改用已安装解释器的绝对路径。脚本依赖 PyYAML 和 markdown-it-py，缺失时在所选 Python 环境安装：

    python -m pip install -r "<Skill目录>/scripts/requirements.txt"

不要把某台机器的解释器路径写进项目规范。下面命令使用单行，按当前 Shell 引用路径；PowerShell 调用带空格的解释器路径时，在引号前使用调用运算符 &。

## 初始化

先列出实际需要的文档；可手工复制模板，不必运行完整脚手架。脚本生成草稿框架，不能把生成文件当作产品需求已完成。

共享布局示例：

    python "<Skill目录>/scripts/scaffold_product_docs.py" --project-root "<项目目录>" --project-name "项目名称" --role "销售员" --role "财务" --module "订单管理" --endpoint "销售员=PC" --endpoint "财务=PC" --layout shared --dry-run

独立业务身份使用 --layout by-identity；--role 此时表达采购商、供应商等身份。--module-role 可指定某模块适用的角色。--scope module 只生成所列模块，不生成项目和端口级文档。只有确认所选范围均有列表与详情页、角色及端口已明确，才使用 --include-core-pages。

预览确认与已授权范围一致后去掉 --dry-run。已有布局自动沿用；脚本不迁移目录。创建前检查路径、元数据与文档ID冲突；同路径已有文档保持原样，只补缺失文件。脚本从已有标准目录恢复模块、身份和端口的名称与编号，改变参数顺序或仅传入一个已有模块不会重新编号。用 --scope module 可只传入新增模块，新编号接在已占用编号之后，不生成项目和端口视图。新建身份页面使用统一端口编号；历史局部编号原样保留。名称规范化冲突、既有映射不唯一、非标准路径或元数据冲突时停止，改为人工核对和补建，不自动改名。

## 选择校验范围

| 范围 | 参数 | 检查边界 |
|---|---|---|
| 已有文档（默认） | --scope present | 检查已有 Markdown 文档，不要求补齐项目目录 |
| 完整默认结构 | --scope project | 额外检查五份项目文档、已有端口和模块的必要文件 |
| 指定模块 | --scope module --module M01 | 可重复 --module；选择完整目录名或唯一模块编号，检查该模块的必要文件 |
| 指定文件 | --scope files --file "相对文档根目录的页面.md" | 可重复 --file，只报告所选文件及关联ID冲突；加载其他文档解析引用定义 |

--docs-dir 指向项目内的文档根目录，默认 docs/product。局部任务选 module 或 files；单模块新建目录也可用 present。

    python "<Skill目录>/scripts/validate_product_docs.py" --project-root "<项目目录>" --scope module --module M01

草稿默认 --phase draft：待确认项与空 sources 作为警告。--phase final 将本次范围待确认项与缺失来源作为错误，是正式交付的最低机械门槛，不代表语义审核通过。--strict 将本次范围所有警告视为失败。范围外仍有待确认的项目不要用全局 strict 代替局部交付判定。

退出码：0 表示本次机械检查未失败；1 表示发现文档问题（或 strict 下存在警告）；2 表示参数／运行环境问题。交付时报告实际错误、警告及未检查范围。

## 元数据与ID

文件开头使用闭合的 YAML frontmatter；doc_id、document_type 为非空字符串，页面类型还需要 page_id。sources 使用非空字符串列表记录可定位的依据，草稿未知时可为空列表。正文不能仅有 frontmatter。支持已有17种正式模板类型；用户要求的补充文档可用 supplement，仍须记录范围和依据，不能用它规避正式页面规格。

文档ID、页面ID在文档树内唯一。业务ID优先在当前模块解析；不同模块的局部ID相同时，跨模块引用要使用能唯一识别的ID。沿用项目既有编号；新建推荐在ID中带模块编号。

自动识别以下前缀的显式引用：REQ、F、BR、RULE、RUL、R、FLD、P、AC、ST、STATE、TR、TRANS、STEP、ACT、EF、TP、OP、CMP、SCN、ERR；形式如 FLD-M01-001。普通正文中的相同形式也按引用检查，围栏代码示例不算业务引用。接入项目时先核对实际编号习惯；额外前缀使用 --id-prefix CUSTOM，可重复传入，仅接受大写字母开头的字母数字串。命令会列出本次自动检查的前缀；其他编号不能宣称已自动覆盖，需要显式声明或人工核对。

权威定义来自对应文档的主表：

| 内容 | 定义位置 |
|---|---|
| 页面 | 页面 frontmatter 的 page_id |
| 需求／公共规则 | 模块主PRD的需求ID／规则ID首列；全局规则可在产品总PRD规则表 |
| 功能 | 模块功能清单的功能主表；功能追踪和身份功能表引用既有ID |
| 字段／字段规则 | 字段字典中含字段名称的字段主表，以及规则ID首列的计算校验表 |
| 流程、状态、动作、影响面、时点、场景与异常 | 流程文档中对应ID首列的定义表；主PRD的边界摘要引用这些场景，不在摘要表重新定义 |
| 操作／组件 | 页面或身份模块主PRD的对应ID首列 |
| 验收 | 验收PRD中的验收ID首列；同文件各专项表可复用同一用例ID |

差异和覆盖表中的字段、功能等仅是引用，不算重新定义。流程中的规则ID引用主PRD或字段字典的规则定义。页面验收摘要引用验收文档；独立页面确需自行定义用例，或项目使用自定义ID／自定义定义表时，在权威文档 frontmatter 的 defines 中显式声明，自定义引用则使用 references。两者均为ID字符串列表，例如：

    defines: [CUSTOM-001]
    references: [CUSTOM-002]

显式声明会参与查重，不能在引用文档里声明 defines 来掩盖丢失的定义。页面与身份文档的重复展示应引用权威ID，不创建第二份定义。拆表后，含名称的主表定义对象，入口、权限、异常与追踪子表复用编号；同一文件中相同编号的稳定名称发生冲突会报错，相同名称的摘要与补充控制信息允许重复。字段主表仍单独检查重复定义，验收专项表可复用用例ID。

## 机械检查与人工审核

脚本检查：YAML结构与重复键、类型和ID、实际标题的最小章节概念、模板变量、待确认项、主表及显式ID定义与引用、本地文件链接目标、Markdown表格列数及表头与分隔行一致性。多个模块同时检查时，每个被选模块都检查必要文件，空模块也报告缺失。章节编号可调整；查询区域与查询条件等已登记同义标题兼容。表格允许转义竖线；链接按Markdown解析，包含引用式链接和图片，不扫描围栏代码中的示例链接。

人工审核：事实来源可信性、业务规则是否正确、字段类型与金额口径、权限与状态一致性、覆盖是否充分、待确认项是否阻塞、Mermaid语法和图表一致性。脚本不访问远程链接、不检查锚点，不自动推断没有显式ID的语义引用，也不证明每个场景均被穷尽。

维护脚本时运行行为回归：

    python "<Skill目录>/scripts/test_product_docs.py"

测试在临时目录生成样例，不操作真实项目。可通过 PRODUCT_DOCS_TEST_TMPDIR 指定临时目录的父路径。
